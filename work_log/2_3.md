# Development Decision History

## 1. 전체 요약

- 초기 목표:
    - Go2와 drone이 함께 있는 fusion simulation에서, drone이 unknown 영역을 밝혀주고 Go2가 그 결과를 이용해 실제로 이동할 수 있게 만드는 것이었다.
    - 특히 Zone C처럼 초기 fused costmap만으로는 Go2가 바로 움직이기 어려운 상황에서, drone scouting이 route discovery에 실질적으로 도움이 되는지를 검증하고 싶었다.
- 현재 목표:
    - `drone_go2_lidar_fusion_sim_agentic_mcp`에서 drone이 먼저 path를 reveal하고, Go2 planner는 그 결과를 바탕으로 실제로 path를 만들며, 필요하면 Go2가 막힌 뒤에도 자동으로 drone recovery가 개입하는 구조를 안정화하는 것이다.
- 가장 큰 방향 전환:
    - 처음에는 `epsilon-optimal`에 가까운 scouting completion 조건을 만족시키는 방향이었지만, 실제로는 fused map의 sparse free-space 표현과 맞지 않아 지나치게 보수적이었다.
    - 이후 “global optimality를 증명하려는 scout” 대신, “현재 Go2 planner가 쓰는 A* 기준으로 path가 생기면 충분하다”는 더 단순한 `path reveal` 방향으로 전환되었다.
- 현재 남아 있는 핵심 쟁점:
    - auto recovery가 실제 simulation에서 과민하게 발동하지 않는지.
    - drone이 밝혀준 free space가 Go2 planner의 runtime behavior와 계속 일관되게 연결되는지.
    - `drone_go2_lidar_fusion_sim_agentic_mcp`에서만 들어간 recovery logic을 다른 fusion blueprint에도 확장할지 여부.

## 2. 의사결정 타임라인

### 1) Epsilon scouting completion 조건이 실제 fused map 표현에 비해 너무 타이트하다는 판단

**당시 목표**

- `fusion_epsilon_scout_then_go2`가 drone scouting 후 적절한 시점에 Go2 goal을 publish하도록 만들고 싶었다.

**원래 계획**

- `corridor_unknown_ratio <= 0.10` 같은 보수적인 epsilon completion 조건을 유지한 채 scout 성공을 판정하려 했다.
- unknown을 거의 제거한 뒤에만 Go2를 보내는 쪽이 더 안전할 것이라고 봤다.

**관찰된 문제 / 새로운 정보**

- 실행 로그에서는 planner가 계속 `Found path 1.1x robot width.`를 찍는데도 epsilon scout은 timeout으로 끝났다.
- drone의 sensor sampling과 fused costmap 표현 특성상, open floor를 충분히 봤어도 unknown cell이 꽤 남을 수 있었다.
- 사용자는 repeated goal loop와 timeout이 실제 정찰 부족이 아니라 판단 기준 문제처럼 보인다고 지적했다.

**변경된 결정**

- 먼저 threshold 완화가 가능한지 검토했고, 실제로 `corridor_unknown_ratio`를 더 느슨하게 보는 안을 시도했다.

**변경 이유**

- 현재 fused map 표현은 sparse free-space promotion 방식이라, `0.10` 같은 기준은 시뮬레이션 표현 수준에 비해 지나치게 엄격했다.

**영향**

- epsilon scout 실패 원인을 “드론이 충분히 못 봤다”가 아니라 “completion criterion이 representation과 맞지 않는다”로 재정의하게 되었다.
- 이후 threshold 완화와 더 근본적인 로직 단순화 논의로 이어졌다.

**확실도**

- 높음

---

### 2) Threshold 완화만으로는 부족하고, epsilon-optimal 로직 자체를 버리기로 한 시점

**당시 목표**

- scouting 성공률을 올리되, 불필요하게 복잡한 optimality 조건은 줄이고 싶었다.

**원래 계획**

- `corridor_unknown_ratio` 같은 threshold만 완화해서 기존 epsilon scouting을 계속 사용할 수도 있다고 봤다.

**관찰된 문제 / 새로운 정보**

- threshold를 완화해도 같은 scout goal이 반복 publish되거나, “조건을 만족했는가”에 대한 논리가 여전히 복잡하게 남아 있었다.
- 사용자는 “epsilon-optimal 로직 자체를 쓰는 게 큰 의미가 없는 것 같다”고 명시적으로 방향 전환을 요청했다.

**변경된 결정**

- `fusion_epsilon_scout_*` 계열과 내부 epsilon helper를 삭제했다.
- 대신 `fusion_reveal_path_then_go2`, `fusion_reveal_path_zone_then_go2`처럼 “Go2의 현재 위치에서 목표까지 갈 수 있는 경로가 생겼는가”만 확인하는 단순한 skill로 바꿨다.

**변경 이유**

- 사용자 목표는 경로 최적성 보장보다 “drone이 route를 열어주고 Go2가 실제로 움직일 수 있느냐”에 더 가까웠다.
- epsilon 조건은 fused map 표현, unknown 처리, completion logic이 모두 얽혀 있어 디버깅 비용이 컸다.

**영향**

- scouting logic의 판단 기준이 `optimality / bound comparison`에서 `path existence`로 단순화되었다.
- tool surface도 `fusion_reveal_path_*` 중심으로 재편되었다.

**확실도**

- 높음

### 3) Path reveal 구현을 “첫 unknown 재발행”이 아니라 frontier reveal 방식으로 고친 시점

**당시 목표**

- `fusion_reveal_path_zone_then_go2("Zone C")`가 실제로 drone을 앞쪽으로 보내면서 route를 열게 하고 싶었다.

**원래 계획**

- Go2 시작점과 목표를 잇는 선분 근처의 unknown을 찾아 drone waypoint로 보내면 충분할 것으로 봤다.

**관찰된 문제 / 새로운 정보**

- 실제로는 `(-1.00, 0.95)` 같은 시작점 근처 waypoint가 계속 반복 선택되며 planner churn이 발생했다.
- 이후 target 근처에 도달한 뒤에도 같은 `Zone C` goal을 0.1초 단위로 계속 재발행하면서 drone이 빙빙 도는 문제가 나타났다.

**변경된 결정**

- reveal waypoint 선택을 “첫 unknown”이 아니라 “현재 drone map bounds 안에서 가장 멀리 있는 unknown frontier” 쪽으로 바꿨다.
- target area 근처에 도달한 뒤에는 짧게 map update settle을 기다리고, 그래도 path가 안 생기면 실패로 종료하도록 바꿨다.

**변경 이유**

- 실제 route reveal은 출발점 근처를 다시 찍는 것이 아니라 unknown frontier를 전진시키는 방식이어야 했다.
- 같은 target을 무한 재발행하면 drone motion이 비정상적으로 보이고 planner churn도 심해졌다.

**영향**

- Zone C 근처에서 drone이 반복 orbit하는 현상이 크게 줄었다.
- reveal-path skill이 “drone이 실제로 front를 밀어내는 정찰”에 더 가까운 behavior를 갖게 되었다.

**확실도**

- 높음

### 4) Conservative path 판정 대신 현재 Go2 A* 판정을 그대로 쓰기로 한 시점

**당시 목표**

- 시각화상으로는 갈 수 있어 보이는 route가 있을 때, skill도 그 사실을 같은 기준으로 인정하게 만들고 싶었다.

**원래 계획**

- fused costmap에서 `UNKNOWN -> OCCUPIED`로 바꾼 뒤 “conservative path exists”를 확인하는 방식이었다.

**관찰된 문제 / 새로운 정보**

- 사용자는 “내가 보기엔 Go2가 충분히 갈 수 있긴 하거든”이라고 말했고, 실제 planner도 runtime에서 unknown에 penalty를 주면서 경로를 찾고 있었다.
- conservative check는 exact target과 unknown 차단을 동시에 요구하므로, 실제 planner behavior보다 더 보수적이었다.

**변경된 결정**

- `fusion_reveal_path_*`의 성공 판정을 `min_cost_astar(...)`의 현재 runtime behavior와 일치시키기로 했다.
- 즉 `UNKNOWN -> OCCUPIED`로 바꾸지 않고, 현재 Go2 planner가 쓰는 fused costmap을 그대로 넣어 path existence를 본다.

**변경 이유**

- reveal skill의 성공 조건과 실제 Go2 planner의 path 생성 기준이 다르면, drone이 충분히 route를 열어줘도 skill은 실패로 판정할 수 있다.
- 사용자 관찰과 code-level planner semantics를 일치시키는 편이 더 실용적이었다.

**영향**

- `fusion_reveal_path_*`는 이제 “실제 Go2가 쓸 수 있는 path가 생겼는가”를 runtime planner와 동일한 기준으로 판단한다.
- 이후 사용자는 drone이 영역을 넓혀주고 Go2가 궤적을 설계하는 것까지 확인했다.

**확실도**

- 높음

### 5) Local OpenAI placeholder key를 코드로 흡수한 시점

**당시 목표**

- 매번 `OPENAI_API_KEY=dummy`를 shell command 앞에 붙이지 않고도 local MCP/agent stack을 실행하고 싶었다.

**원래 계획**

- local OpenAI-compatible endpoint를 쓸 때도 환경변수로 `OPENAI_API_KEY=dummy`를 수동 지정했다.

**관찰된 문제 / 새로운 정보**

- 사용자는 `ChatOpenAI` 초기화 단계에서 `api_key client option must be set` 에러가 뜬다고 보고했다.
- 실제 실행 환경의 `openai_base_url`은 `http://127.0.0.1:10531/v1` 같은 local endpoint였다.

**변경된 결정**

- `create_chat_model()`에서 local host 계열 `openai_base_url`을 쓸 때, `OPENAI_API_KEY`가 비어 있으면 자동으로 placeholder `dummy`를 넣도록 바꿨다.

**변경 이유**

- local OpenAI-compatible server에는 실질적인 credential 검증이 필요 없는데, 라이브러리 초기화 조건 때문에 매번 dummy key를 넣는 것은 불필요한 UX 마찰이었다.

**영향**

- 이후 `uv run dimos ...` 같은 command를 실행할 때 매번 `OPENAI_API_KEY=dummy`를 붙일 필요가 없어졌다.
- 다만 실제 OpenAI API를 쓸 경우에는 여전히 진짜 key가 필요하도록 fallback 범위를 local host에만 제한했다.

**확실도**

- 높음

### 6) Go2가 막힌 뒤 drone recovery를 자동으로 호출하는 구조를 넣은 시점

**당시 목표**

- Go2가 스스로 여러 번 재계획해도 목적지에 못 가는 경우, drone이 자동으로 개입해 path reveal을 수행하게 만들고 싶었다.

**원래 계획**

- 처음에는 planner 내부의 `stuck -> replan`만으로 충분할 수 있다고 봤다.
- drone scouting은 agent나 사용자가 명시적으로 호출하는 skill로만 두었다.

**관찰된 문제 / 새로운 정보**

- 코드상으로는 `Go2 stuck -> automatic replan`은 있었지만, `Go2 stuck -> drone scout 호출`은 전혀 연결돼 있지 않았다.
- 사용자는 “Go2가 막혔다는 걸 알 수 있다면, Go2 막힘 -> Drone으로 현재 Go2 위치에서 목적지까지 이동하면서 영역 밝히기 -> Go2 재계획” 구조를 원했다.

**변경된 결정**

- planner가 external recovery를 요청하는 `recovery_goal` event를 emit하도록 바꿨다.
- `drone_go2_lidar_fusion_sim_agentic_mcp`의 fusion skill container가 이 event를 받아 background auto recovery thread를 시작하도록 했다.
- recovery는 기존 `fusion_reveal_path` 로직을 재사용하고, 성공 시에만 원래 Go2 goal을 다시 publish한다.
- recovery 중에는 duplicate trigger를 막고, 더 새로운 Go2 goal이 관측되면 현재 recovery를 취소하도록 했다.

**변경 이유**

- planner가 막힘을 감지할 수 있어도, map이 부족한 문제는 Go2 혼자 재계획만 반복해서는 해결되지 않는다.
- 이미 구현된 reveal-path logic을 재사용하면 “drone이 route를 열고, Go2 planner가 같은 goal을 다시 시도”하는 recovery loop를 큰 구조 변경 없이 만들 수 있다.

**영향**

- `drone_go2_lidar_fusion_sim_agentic_mcp`에서는 이제 Go2 navigation failure가 drone-assisted recovery로 이어질 수 있게 되었다.
- recovery는 planner 내부가 아니라 fusion layer에서 동작하므로, 기존 planner와 skill 계층의 역할 분리는 유지된다.

**확실도**

- 높음

### 7) Auto recovery trigger를 “replan exhausted만”이 아니라 “No path found / 3회 이상 replan”까지 앞당긴 시점

**당시 목표**

- Go2가 너무 오래 self-replan만 반복하기 전에 drone을 더 빨리 보내고 싶었다.

**원래 계획**

- auto recovery는 `ReplanLimiter`가 완전히 소진되었을 때만 시작되도록 했다.

**관찰된 문제 / 새로운 정보**

- 사용자는 두 조건을 추가로 원했다.
    - `No path found to the goal`
    - 경로 replanning을 `3번 이상` 했는데도 목적지에 도달하지 못한 경우

**변경된 결정**

- planner에서 external recovery trigger 조건을 세 갈래로 정리했다.
    - `No path found to the goal`
    - replan attempt가 `3회 이상`
    - 기존처럼 replan limiter가 완전히 소진된 경우

**변경 이유**

- 실제로 map 부족 상황이라면 planner가 6회까지 모두 소진할 때까지 기다리는 것은 너무 느릴 수 있다.
- `No path found`는 곧바로 drone map expansion이 필요한 신호일 가능성이 크고, `3회 이상 replan`도 충분한 실패 신호로 볼 수 있었다.

**영향**

- drone recovery가 더 이른 시점에 개입하게 되었다.
- planner는 self-replan과 external recovery 사이를 더 공격적으로 전환하게 되었고, 이에 대한 runtime tuning 필요성도 함께 커졌다.

**확실도**

- 높음

## 3. 주요 변경점만 따로 정리

- `fusion_epsilon_scout_*` 계열을 제거하고 `fusion_reveal_path_*` 중심으로 단순화했다.
- path reveal 성공 기준을 conservative check가 아니라 현재 Go2 planner의 `min_cost_astar(...)` behavior와 일치시켰다.
- Zone C 근처에서 같은 goal을 재발행하며 drone이 빙빙 도는 현상을 줄이기 위해 frontier selection과 target settle logic을 보강했다.
- local host `openai_base_url`에서는 `OPENAI_API_KEY=dummy`를 수동으로 넣지 않아도 되도록 fallback을 추가했다.
- Go2 planner에 external recovery event를 추가하고, `drone_go2_lidar_fusion_sim_agentic_mcp`에서 auto drone recovery를 수행하도록 연결했다.
- auto recovery trigger는 이제 `No path found`, `3회 이상 replan`, `replan exhausted` 세 경우에 발동한다.
