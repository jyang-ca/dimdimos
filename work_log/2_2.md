# Development Decision History

## 1. 전체 요약

- 초기 목표:
    - Drone과 Go2를 동시에 deploy하고, 각 객체가 수집한 데이터를 서로 공유하게 만드는 것.
    - 특히 “drone lidar로 만든 map/costmap을 Go2 navigation에 활용할 수 있는가”가 핵심 질문이었
    다.
- 현재 목표:
    - drone-go2-lidar-fusion-sim-agentic-mcp에서 agent가 명령을 이해하고, drone과 Go2를 기종별로
    분리 제어하며, drone이 먼저 unknown 영역을 정찰한 뒤 그 결과가 Go2 fused costmap에 반영된
    상태에서 Go2를 이동시키는 것.
    - Zone C처럼 drone costmap bounds 밖에 있는 목표도 한 번에 보내지 않고, 중간 waypoint를 반복
    생성하면서 실제로 정찰이 완료될 때까지 이어가는 방향으로 바뀌었다.
- 가장 큰 방향 전환:
    - 처음에는 “기존 drone에 lidar를 붙여 deploy”하는 방향이었지만, 실제 하드웨어 드론/DJI/
    RosettaDrone/UDP가 아니라 “MuJoCo 같은 시뮬레이션 환경에서 Go2와 drone을 같이 deploy”하는
    요구로 전환되었다.
    - 이후 단순히 drone costmap을 Go2에 연결하는 것에서, “fusion 전용 blueprint 안에서만 drone
    map을 Go2 fused costmap에 반영하고, agentic skill이 정찰 완료 조건을 확인한 뒤 Go2 goal을
    발행”하는 구조로 발전했다.
- 현재 남아 있는 핵심 쟁점:
    - drone scout loop의 실제 런타임 안정성: waypoint 반복, stuck 판단, map bounds 확장 여부가 실
    제 시뮬레이션에서 충분히 자연스럽게 동작하는지.
    - Go2가 fused costmap을 실제 planning에서 얼마나 의미 있게 사용하고 있는지.
    - UI와 agentic skill의 goal/cmd/path topic 분리가 완전히 의도대로 유지되는지.
    - Zone 정의와 “Zone C 근처”의 의미가 현재 hardcoded zone 중심 좌표 기준으로 충분한지.

## 2. 의사결정 타임라인

### 1. Drone-Go2 데이터 공유 가능성 검토

- 당시 목표:
    - Drone과 Go2를 동시에 deploy하고, 각 객체가 수집하는 데이터를 서로 공유하게 만들고 싶었다.
    - 사용자는 “지금은 costmap이 각각 구분되어 있는 걸로 알고 있어”라고 전제했다.
- 원래 계획:
    - 우선 기존 drone 장치에 lidar를 추가한 새 drone blueprint를 만들고 deploy해보자는 방향.
    - drone-lidar-basic, drone-lidar-mapping 같은 단계적 blueprint를 생각했다.
- 관찰된 문제 또는 새로운 정보:
    - global map/costmap이 정상 생성되는지 확인할 metric이 필요했다.
    - unknown_percent, occupied_percent, voxel_count, bbox_extent, timestamp_lag_ms 같은 metric을
    기준으로 검증하려 했다.
- 변경된 결정:
    - drone lidar blueprint 구현 전에 map/costmap health metric을 검증 기준으로 삼기로 했다.
    - 이후 drone-lidar-basic, drone-lidar-mapping 구현 및 테스트 작성으로 진행했다.
- 변경 이유:
    - 단순히 topic이 publish되는지만으로는 mapping이 정상인지 판단하기 어렵기 때문.
    - 특히 fusion의 전제가 “drone map이 실제로 생성되고 갱신된다”는 것이어서 metric 기반 검증이
    필요했다.
- 영향:
    - 이후 테스트 설계에서 unknown_percent, occupied_percent, voxel_count, bbox_extent,
    timestamp_lag_ms가 중요한 검증 항목이 되었다.
- 확실도: 높음

    행.
    - DroneConnectionModule, FastLio2, DroneCameraModule 등을 포함하는 실제 drone blueprint 흐름
    이었다.

    - 실행 로그에서 nix build .#fastlio2_native가 실패했다.
    - 원인은 nix: not found.
    - 사용자는 “나는 이 서버에 sudo 권한이 없어”, “가상환경에서만 실행할꺼야”라고 제약을 밝혔다.
    - 이후 “내가 말하는 가상환경은 mujoco 같은 환경이야”라고 clarified 했다.
- 변경된 결정:
    - 실제 DJI/RosettaDrone/UDP 기반 drone deploy가 아니라, Go2와 같이 동작하는 simulation drone
    을 구현하는 방향으로 전환.
    - DroneSimConnectionModule + drone-lidar-mapping-sim 구현이 결정되었다.
- 변경 이유:
    - 실제 drone blueprint는 DJI drone, RosettaDrone Android app, MAVLink UDP 14550, video UDP
    5600, FastLio2 native build 등 하드웨어/시스템 의존성이 있었다.
    - 사용자의 목표는 하드웨어가 아니라 “MuJoCo 같은 시뮬레이션 환경에서 drone과 Go2를 같이
    deploy”하는 것이었다.
    - sudo 권한도 없으므로 apt/nix 설치 전제는 맞지 않았다.
- 영향:
    - 이후 모든 개발 방향은 실제 drone 장치가 아니라 simulation module 중심으로 바뀌었다.
    - DroneSimConnectionModule, simulated lidar, simulated odom/cmd_vel, sim blueprint가 핵심이
    되었다.
- 확실도: 높음

### 3. drone-lidar-mapping-sim 구현과 click goal 이동

- 당시 목표:
    - simulation 환경에서 drone lidar mapping blueprint를 만들고, command center에서 click goal로
    drone을 이동시키고 싶었다.
- 원래 계획:
    - DroneSimConnectionModule이 lidar/odom/cmd_vel을 publish/subscribe하고, mapper/planner가 이
    를 사용.
    - drone-lidar-mapping-sim에서 drone이 lidar map을 만들고 costmap도 생성.
- 관찰된 문제 또는 새로운 정보:
    - click goal 로그는 나오지만 drone 이동이 기대와 다르거나 곡선 궤적이 나왔다.
    - 사용자는 “드론이 목적지로 이동하는 궤적이 직선이 아니거든?”이라고 지적했다.
- 변경된 결정:
    - click goal에 대해서도 drone이 움직이도록 구현.
    - 곡선 경로는 Go2용 A* / local planner 흐름을 재사용해서 생긴 것으로 해석했다.
- 변경 이유:
    - 초기 구현은 drone 전용 비행 제어라기보다 기존 ground robot navigation stack을 재사용하는 방
    향이었다.
    - 그래서 드론이 공중에서 직선 이동하는 모델이 아니라, costmap 기반 planar navigation 경로를
    따라갔다.
- 영향:
    - 이후 “drone은 공중 이동체이므로 ground obstacle을 그대로 피하면 안 된다”는 문제로 이어졌다.
    - 이 판단이 DroneFlightCostMapper 도입의 배경이 되었다.
- 확실도: 높음

### 4. Go2와 동일한 simulation 공간으로 정렬

- 당시 목표:

    만들고 싶었다.
- 원래 계획:
    - drone sim은 독립적인 공간/scene을 사용할 수 있었다.
- 관찰된 문제 또는 새로운 정보:
    - 사용자는 Go2와 drone을 같은 시뮬레이션 환경에서 같이 deploy하고 싶었다.
    - costmap fusion을 하려면 두 robot의 world frame과 환경이 맞아야 했다.
- 변경된 결정:
    - drone sim scene을 Go2 simulation 환경과 맞추는 방향으로 수정.
    - 이후 fusion blueprint에서도 같은 공간을 전제로 topic을 분리하고 map을 합성했다.

    - 좌표계와 공간이 다르면 drone map을 Go2 costmap에 투영할 수 없다.

- 영향:
    - 이후 /drone/global_map, /go2/global_map, /go2/fused_global_costmap 같은 topic 분리가 의미
    있게 가능해졌다.
- 확실도: 높음

### 5. Drone lidar의 공중 레이어 문제와 height filtering

- 당시 목표:
    - Rerun 3D map에서 공중에 보이는 이상한 layer가 실제 장애물인지 sensor artifact인지 판단하고
    제거하고 싶었다.
- 원래 계획:
    - simulated lidar point cloud를 그대로 mapping에 사용.
- 관찰된 문제 또는 새로운 정보:
    - 사용자가 “공중에 뭔가 레이어 같은게 보여. lidar 센서가 물체가 있다고 착각하는 것 같은데”라
    고 보고했다.
    - 분석 결과 drone lidar frame에서 world-height cap 또는 vertical FOV filtering이 필요하다고
    판단했다.
- 변경된 결정:
    - DroneSimConnectionModule._lidar_frame()에 z <= 2.5 같은 world-height cap 또는 sensor-
    relative vertical FOV 필터를 적용.
    - 왜 이 필터가 필요한지 주석을 추가.
- 변경 이유:
    - sim scene geometry 또는 lidar sampling이 천장/상단 구조물을 drone 주변 obstacle처럼 과도하
    게 반영하는 문제가 있었다.
    - drone mapping 품질이 나빠지면 costmap과 fusion에도 직접 악영향이 생긴다.
- 영향:
    - 공중 layer artifact를 줄이고, drone/global_map의 신뢰도를 높이는 방향으로 수정되었다.
- 확실도: 높음

### 6. Drone costmap과 Go2 costmap 분리

- 당시 목표:
    - simulation 환경에서 drone costmap을 Go2 costmap에서 분리하는 것이 좋은지 판단.
- 원래 계획:
    - 초기에는 global costmap을 공유하거나 같은 topic을 사용할 여지가 있었다.
- 관찰된 문제 또는 새로운 정보:
    - drone과 Go2는 이동 방식과 obstacle 해석이 다르다.
    - Go2는 ground robot이고, drone은 obstacle height에 따라 통과 가능 여부가 달라진다.
- 변경된 결정:
    - drone output을 /drone/global_map, /drone/global_costmap 계열로 분리.
    - Go2는 /go2/global_costmap을 사용하도록 분리.
    - fusion은 별도 /go2/fused_global_costmap으로 만들기로 했다.
- 변경 이유:
    - 같은 obstacle이라도 drone과 Go2의 cost 해석이 다르기 때문.
    - topic을 공유하면 planner가 서로 다른 semantics를 가진 costmap을 오해할 수 있다.
    - 이후 fusion을 특정 blueprint에만 적용하려면 namespace 분리가 필수였다.
- 영향:
    - drone-only blueprint와 Go2-only blueprint가 오염되지 않게 되었다.
    - fusion logic은 전용 blueprint에서만 활성화하는 구조가 가능해졌다.
- 확실도: 높음

### 7. DroneFlightCostMapper 도입

- 당시 목표:
    - drone이 장애물을 피하는 경로를 선택하는 문제를 개선.
    - 사용자는 “드론은 공중에서 이동하기 때문에 장애물의 높이를 측정하고 드론의 현재 높이 보다 낮
    다면 통과할 수 있어야돼”라고 요구했다.
- 원래 계획:
    - 기존 CostMapper(simple)를 사용해 point cloud를 2D occupancy grid로 투영.
- 관찰된 문제 또는 새로운 정보:
    - 기존 costmap은 ground robot 관점이다.
    - 낮은 장애물도 2D grid에서는 occupied가 되어 drone 경로를 막았다.
- 변경된 결정:
    - DroneFlightCostMapper를 추가.
    - 입력은 /drone/global_map, odom.
    - 출력은 /drone/global_costmap.
    - 현재 고도 band와 겹치는 obstacle만 occupied로 해석.
    - 낮은 obstacle은 free, 높은 벽/천장은 occupied 또는 configurable policy로 처리.
- 변경 이유:
    - drone navigation costmap은 “XY 위치에 장애물이 있는가”가 아니라 “현재 비행 고도에서 충돌 위
    험이 있는가”를 봐야 한다.
    - ground robot용 costmap을 그대로 쓰면 drone의 장점이 사라진다.
- 영향:
    - drone planner가 공중 이동체 semantics에 맞는 costmap을 사용하게 되었다.
    - 이 결정은 이후 drone map과 Go2 map을 분리해야 하는 강한 근거가 되었다.
- 확실도: 높음

### 8. Drone map을 Go2가 이용하기 위한 fusion blueprint 설계

- 당시 목표:
    - drone이 이동하며 만든 costmap/map을 Go2가 이용하게 하고 싶었다.
    - 사용자는 “drone-sim-lidar + go2-sim 을 위한 blueprint”를 만들고, fusion costmap logic은 해
    당 blueprint에서만 적용되길 원했다.
- 원래 계획:
    - Go2가 기존 /go2/global_costmap을 사용하고, drone map을 추가 layer로 활용.
- 관찰된 문제 또는 새로운 정보:
    - 기존 drone-lidar-mapping-sim, unitree-go2에는 영향이 없어야 했다.
    - drone과 Go2 goal/cmd/path도 topic이 섞이면 안 되었다.
- 변경된 결정:
    - drone-go2-lidar-fusion-sim 전용 blueprint 생성.
    - DroneFusionPlanner 추가.
    - /drone/*, /go2/*로 goal/cmd/path를 완전히 분리.
    - Go2 bottom map은 /go2/fused_global_costmap 표시.
    - drone map click은 /drone/goal_request, Go2 map click은 /go2/goal_request.
- 변경 이유:
    - fusion은 실험적이고 특정 mission 전용이므로 기존 blueprints에 영향을 주면 안 된다.
    - 두 robot의 command topic이 섞이면 command center click이 잘못된 robot을 움직일 수 있다.
    - Go2가 drone 정보를 활용하는 것은 “기본 Go2 behavior”가 아니라 “fusion sim behavior”로 제한
    해야 했다.
- 영향:
    - fusion이 새 blueprint scope에 격리되었다.
    - UI도 robot-specific map interaction 구조로 바뀌었다.
- 확실도: 높음

### 10. Fused costmap 생성 중 Pose origin bug 수정

- 당시 목표:
    - drone이 움직일 때 Go2 fused costmap도 업데이트되는지 검증.
- 원래 계획:
    - Go2CostmapFusion이 /go2/global_costmap과 /go2/drone_obstacle_layer를 합쳐 /go2/
    fused_global_costmap을 publish.
- 관찰된 문제 또는 새로운 정보:
    - 로그에 AttributeError: 'Pose' object has no attribute 'x'.
    - 문제 위치는 drone_fusion_costmap.py, origin.position.x = origin_x.
    - 즉 origin 자체가 아니라 origin.position.x에 접근해야 하는 message 구조 문제가 있었다.
- 변경된 결정:
    - LCM-decoded origin/Pose 구조에 맞게 origin assignment를 수정.
- 변경 이유:
    - occupancy grid origin은 Pose이고, 좌표는 origin.position.x/y에 있어야 한다.
    - 이 오류 때문에 fused costmap publish가 반복 실패했을 가능성이 높았다.
- 영향:
    - fused costmap update pipeline이 정상화되었다.
    - 이후 Go2 map visual 변화 여부를 더 정확히 검증할 수 있게 되었다.
- 확실도: 높음

### 11. Drone map이 Go2 path 선택에 충분히 반영되지 않는 문제

- 당시 목표:
    - 사용자가 제시한 시나리오:
        - Go2는 이미 가본 A -> B -> Z 경로로 이동 가능.
        - 실제 최적 경로는 A -> C -> Z.
        - C 경로는 drone이 접근했던 경로라 fusion이 제대로 되면 Go2가 알 수 있어야 한다.
- 원래 계획:
    - drone obstacle/free layer를 Go2 fused costmap에 단순 overlay.
- 관찰된 문제 또는 새로운 정보:

## 5. 최종적으로 복원한 현재 기준

- 현재 채택된 개발 방향:
    - simulation-first multi-robot fusion.
    - drone과 Go2는 각각 독립 namespace를 가진다.
    - drone은 aerial mapper로서 unknown/free/obstacle 정보를 수집한다.
    - Go2는 ground robot으로서 /go2/fused_global_costmap을 사용한다.
    - fusion logic과 agentic behavior는 drone-go2-lidar-fusion-sim-agentic-mcp 전용으로 제한한다.
    - agent는 known zone name을 직접 resolve하고, robot-specific skill을 호출한다.
    - drone scout는 단발 goal이 아니라 bounds-aware waypoint mission loop로 동작한다.
    - Go2 goal은 drone scout completion gate 이후에만 발행한다.
- 현재 우선순위:
    - 안정적인 scout orchestration.
    - drone map이 Go2 fused costmap에 실제 정보로 반영되는 것.
    - topic namespace 격리.
    - 기존 standalone drone/Go2 blueprints에 영향 주지 않기.
    - 테스트로 regression 방지.
- 현재 비목표(non-goal):
    - 실제 DJI drone deploy 지원.
    - RosettaDrone/UDP/MAVLink/video stream 문제 해결.
    - system-level nix/apt 설치 문제 해결.
    - 완전한 3D aerial planner 구현.
    - 모든 blueprint에 fusion logic을 일반화 적용.
    - Go2 기본 blueprint의 navigation behavior를 바꾸는 것.
