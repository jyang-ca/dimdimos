# Development Decision History

## 2. 의사결정 타임라인

### 1. 센서 기반 자율 임무 생성 방향을 정한 시점
- 당시 목표:
  - [explicit][높음] 시뮬레이션 내 센서 데이터, 예를 들어 구역별 온도나 시각 변화, 를 agent가 스스로 감지해 임무를 생성하는 로직을 구상하는 것이었다.
  - [explicit][높음] 사용자는 이를 “센서 데이터가 message queue에 고수준 임무를 전달”하는 형태로 생각했다.
- 원래 계획:
  - [explicit][중간] 처음에는 “시뮬레이션 내의 센서 데이터”라고 표현했으므로 MuJoCo 환경 자체에 환경 변수나 센서 상태를 넣는 방향도 후보였다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] 사용자가 “일단 mujoco에서 환경 변수를 넣기는 싫으니까”라고 제약을 명확히 했다.
  - [explicit][높음] 사용자는 Google Spreadsheet CSV를 주기적으로 읽는 방식을 제안했다. 근거 표현: `curl -L ".../export?format=csv&gid=0"`로 “구역/시간 별 온도 정보가 나오잖아”.
- 변경된 결정:
  - [explicit][높음] MuJoCo 내부 환경 변수 대신 외부 CSV feed를 polling하는 방식으로 전환했다.
  - [inferred][높음] Spreadsheet는 실제 센서 연동 전의 임시 external sensor interface로 취급하기로 했다.
- 변경 이유:
  - [explicit][높음] 사용자가 MuJoCo 내부 상태 주입을 피하고 싶어 했다.
  - [inferred][높음] 외부 feed polling은 빠르게 end-to-end를 검증할 수 있고, 나중에 실제 센서 feed로 교체하기 쉽다.
- 영향:
  - [explicit][높음] sensor polling process가 필요해졌다.
  - [inferred][높음] sensor source와 mission generation을 분리하는 abstraction이 중요해졌다.
- 확실도: [높음]

### 2. `TemperatureSheetMonitor`에서 generic sensor monitor로 바꾼 시점
- 당시 목표:
  - [explicit][높음] 온도 데이터를 바탕으로 message queue에 명령을 날리는 프로세스를 만드는 것이었다.
- 원래 계획:
  - [explicit][높음] 사용자는 예시로 `TemperatureSheetMonitor` 같은 이름을 언급했다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] 사용자가 “spreadsheet는 임시로 내가 사용하는 인터페이스니까, 내부적으로 sheet이라는 이름을 사용하지 말고”라고 수정했다.
  - [explicit][높음] 사용자는 “일단 온도만 모니터링 할 게 아니니까”라고도 말했다.
- 변경된 결정:
  - [explicit][높음] sheet/temperature에 묶인 이름이 아니라 `SensorMissionMonitor`처럼 “센서들을 모니터링하는 프로세스”라는 의미의 generic module로 설계했다.
- 변경 이유:
  - [explicit][높음] Spreadsheet는 임시 interface이고, 장기 abstraction은 sensor monitoring이어야 했다.
  - [inferred][높음] 온도 외 변수나 시각 변화 같은 다른 sensor signal로 확장하려면 source-specific naming을 피해야 했다.
- 영향:
  - [explicit][중간] 내부 vocabulary가 sheet 중심이 아니라 sensor feed, trigger rule, mission event 중심으로 정리되었다.
  - [inferred][높음] 나중에 spreadsheet 대신 다른 API, file, robot sensor, vision detector를 붙여도 module 이름과 책임을 유지할 수 있게 되었다.
- 확실도: [높음]

### 3. Sensor event를 직접 robot command가 아니라 agent message로 넣기로 한 시점
- 당시 목표:
  - [explicit][높음] 특정 구역의 온도가 너무 높으면 로봇이 해당 구역으로 이동하도록 만드는 것이었다.
- 원래 계획:
  - [explicit][높음] 사용자는 DimOS에 “로봇에게 명령을 전달 할 수 있는 message queue”가 있고, 그 안에 “skill들이 들어갈 수 있잖아”라고 설명했다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] DimOS에는 MCP/agent/skill 구조가 있고, high-level skill을 tool로 호출할 수 있다.
  - [inferred][중간] sensor monitor가 navigation command를 직접 publish하면 agent의 판단, 발화, skill selection 흐름을 우회하게 된다.
- 변경된 결정:
  - [explicit][높음] sensor monitor는 low-level command를 직접 발행하지 않고, agent에게 high-level mission message를 넣는다.
  - [explicit][높음] message에는 `inspect_zone`을 호출하라는 recommendation과 `zone_name`, `reason`, threshold/value/severity 정보를 포함한다.
- 변경 이유:
  - [inferred][높음] 기존 message queue와 skill 호출 구조를 재사용하면 user command와 autonomous trigger가 같은 agent decision path를 탄다.
  - [inferred][중간] agent가 “briefly speak what you are doing” 같은 부가 행동도 함께 수행할 수 있다.
- 영향:
  - [explicit][높음] 실제 로그에서 sensor event가 `human` message로 들어가고 agent가 `agent_send`, `inspect_zone` tool call을 수행했다.
  - [inferred][높음] sensor monitor의 책임은 mission producer/gatekeeper가 되고, 실제 actuation은 agent/skill layer에 남았다.
- 확실도: [높음]

### 4. Zone inspection을 agent prompt 조합이 아니라 composite skill로 만든 시점
- 당시 목표:
  - [explicit][높음] `ZoneA temp 100C` 같은 이벤트가 발생하면 로봇이 Zone A로 이동하고, Zone A 중심 기준으로 둥글게 돌면서 각 view 사진을 찍게 하는 것이었다.
- 원래 계획:
  - [explicit][높음] 사용자는 “1. Zone A 로 이동 2. Zone A의 중심을 기준으로 둥글게 돌면서 3. 각 뷰에 대한 사진”을 원했다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] DimOS skill은 agent에게 tool로 노출될 수 있다.
  - [inferred][높음] agent가 매번 low-level 이동, 회전, 촬영을 prompt로 조합하면 재현성과 실패 처리가 약해진다.
- 변경된 결정:
  - [explicit][높음] `inspect_zone`이라는 composite skill을 만들고, agent는 이 skill 하나를 호출하도록 했다.
  - [explicit][중간] skill 내부에서 known zone lookup, navigation goal 생성, camera frame capture, output directory 반환을 처리하게 했다.
- 변경 이유:
  - [inferred][높음] Zone inspection은 domain action이므로 skill로 캡슐화하는 편이 테스트 가능하고 안정적이다.
  - [inferred][중간] agent prompt는 “critical event면 inspect_zone을 호출하라”는 간단한 규칙으로 유지할 수 있다.
- 영향:
  - [explicit][높음] 로그에 `tool=inspect_zone`, `Navigating to zone inspection viewpoint`가 나타났다.
  - [explicit][높음] 실패도 skill return string으로 agent에 전달됐다. 예: “failed to reach viewpoint 0 within 60s”.
- 확실도: [높음]

### 5. 임시 Zone 좌표를 실제 simulation 좌표계에 맞추기로 한 시점
- 당시 목표:
  - [explicit][높음] `unitree-go2-agentic-mcp` simulation에서 Zone A/B/C 중심 좌표를 실제 이동 가능한 좌표로 조정하는 것이었다.
- 원래 계획:
  - [explicit][높음] Zone A/B/C 좌표는 임시 좌표였다. 사용자가 직접 “현재는 임시 좌표입니다. -> 진행해줘”라고 말했다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] planner 로그에서 `No path found to the goal`이 반복됐다.
  - [explicit][높음] 예시 goal: Zone A 쪽 `x=2.05 y=7.99`, Zone B 쪽 `x=4.7 y=0.89`, Zone C 쪽 `x=2.68 y=-5.98`.
  - [explicit][높음] 사용자는 “로봇이 초기위치(움직일 수 있는 범위)에 있는데 ... 로봇이 안움직이고 있어”라고 보고했다.
- 변경된 결정:
  - [explicit][높음] Zone 좌표를 실제 simulation 환경, costmap, planner가 인식하는 좌표계에 맞춰 다시 잡기로 했다.
  - [inferred][중간] 단순히 zone center만 맞추는 것이 아니라 inspection waypoint radius도 도달 가능성을 고려해야 한다.
- 변경 이유:
  - [explicit][높음] 임시 좌표 또는 그 주변 waypoint가 planner 기준으로 unreachable이었다.
  - [inferred][높음] explored map bounds, obstacle inflation, frame id, goal position이 실제 navigation 가능 여부에 직접 영향을 줬다.
- 영향:
  - [explicit][높음] 이후 debugging은 실제 click goal, odom 위치, path found 여부를 보면서 좌표를 조정하는 흐름으로 바뀌었다.
  - [inferred][중간] Zone definition이 inspection skill뿐 아니라 UI marker와도 연결되어야 할 필요가 커졌다.
- 확실도: [높음]

### 6. Multi-view circular inspection의 안정성 문제를 발견한 시점
- 당시 목표:
  - [explicit][높음] autonomous sensor event가 들어오면 Zone inspection이 실제로 완료되어야 했다.
- 원래 계획:
  - [explicit][높음] Zone 중심 주변 여러 viewpoint를 순회하며 사진을 찍는 route였다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] Zone C는 local planner가 goal에 도달한 것처럼 보이는 로그가 있었지만, skill은 “failed to reach viewpoint 0 within 60s”를 반환한 사례가 있었다.
  - [explicit][높음] Zone B는 viewpoint 0은 도달했지만 viewpoint 1에서 stuck/replan 후 실패했다.
  - [explicit][높음] local planner에서 `ValueError: More than 5% of path points are occupied`가 발생했다.
- 변경된 결정:
  - [inferred][중간] route 전체를 성공시키는 것보다, 우선 도달 가능한 Zone inspection point와 명확한 capture 결과를 안정화하는 쪽으로 무게가 이동했다.
  - [inferred][중간] 현재 코드 상태에서는 `inspect_zone`이 one camera view capture로 단순화되어 있어, multi-view route 실패 경험이 이 방향 전환의 배경이었을 가능성이 크다.
- 변경 이유:
  - [explicit][높음] multi-view route는 각 waypoint가 모두 reachable이어야 하므로 실패 표면이 컸다.
  - [inferred][높음] autonomous trigger가 반복될 때 긴 timeout과 재시도는 agent queue를 막고 중복 발화를 만들 수 있다.
- 영향:
  - [explicit][중간] prompt와 skill 쪽에서는 `inspect_zone`을 low-level movement/camera step으로 분해하지 않는 방향이 강화됐다.
  - [inferred][중간] single-view inspection과 multi-view inspection 사이의 제품 요구 충돌이 남았다.
- 확실도: [중간]

### 7. Sensor event 반복과 queue 관리 필요성을 인식한 시점
- 당시 목표:
  - [explicit][높음] critical temperature event가 발생하면 agent가 적절히 반응하게 하는 것이었다.
- 원래 계획:
  - [explicit][높음] CSV 최신 row에서 threshold crossing을 감지하면 event를 주입한다.
- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] 로그에서 Zone B inspection 실패 이후 “Inspecting Zone B for high temperature” 같은 message가 반복됐다.
  - [explicit][높음] Zone B inspection 중 Zone C event가 들어오는 등 mission이 겹치는 상황도 나타났다.
- 변경된 결정:
  - [explicit][중간] monitor에는 event key, cooldown, agent idle 같은 gatekeeping이 필요해졌다.
  - [inferred][중간] critical event와 noncritical event의 처리 정책을 다르게 둬야 한다.
- 변경 이유:
  - [inferred][높음] 같은 spreadsheet row 또는 같은 threshold 상태를 계속 polling하면 같은 mission이 반복될 수 있다.
  - [inferred][중간] 모든 event를 즉시 실행하면 진행 중인 inspection과 충돌한다.
- 영향:
  - [explicit][중간] monitor는 단순 polling loop가 아니라 deduplication/cooldown을 가진 mission gatekeeper가 되었다.
  - [inferred][중간] 중첩 critical event의 queueing/cancellation policy는 여전히 unresolved로 남았다.
- 확실도: [중간]

### 8. LCM Pose decoding 오류를 runtime 안정성 이슈로 처리한 시점
- 당시 목표:

- 원래 계획:

- 관찰된 문제 또는 새로운 정보:
  - [explicit][높음] 로그에 `AssertionError: <class 'dimos.msgs.geometry_msgs.Pose.Pose'> not stringified type hint.`가 발생했다.

- 변경된 결정:

- 변경 이유:
  - [inferred][높음] high-rate LCM callback 중 lazy dispatch registration이 race를 일으킬 가능성이 있었기 때문이다.
- 영향:
  - [explicit][중간] sensor/zone 기능 자체의 요구는 아니지만, 전체 runtime 검증을 막는 blocking bug로 처리됐다.
  - [explicit][중간] 이후 `ruff`, `py_compile`, `mypy`, 관련 pytest로 검증했다.
- 확실도: [중간]

## 4. 아직 unresolved 인 것

- 아직 결정되지 않은 문제
  - [inferred][중간] 최종 `inspect_zone`이 multi-view circular inspection이어야 하는지, single-view stable inspection이어야 하는지 아직 제품적으로 확정되지 않았다.
  - [inferred][중간] critical event가 inspection 진행 중 겹칠 때 queueing, cancellation, priority를 어떻게 처리할지 명확하지 않다.
  - [inferred][중간] `ValueError: More than 5% of path points are occupied`의 근본 해결은 navigation/path clearance tuning 영역으로 남아 있다.
- 대화상 애매하게 남아 있는 부분
  - [inferred][낮음] 사용자가 말한 “왼쪽 패널”이 2D command center visualization 전체를 의미하는지, 별도 list/sidebar UI를 의미하는지 불확실하다. 구현은 marker visualization 기준으로 진행됐다.
  - [explicit][중간] 사진 저장 path는 작업 시점에 따라 달랐다. 대화 중 확인된 경로는 `/tmp/dimos_zone_inspections`였고, 현재 작업 내역에는 repo 내부 `temp/dimos_zone_inspections`가 보인다. 실제 실행 기준 path는 skill return message로 확인해야 한다.
  - [inferred][중간] Zone A/B/C의 이름이 실제 office scene의 어떤 semantic area를 의미하는지, 사용자의 기대와 완전히 일치하는지는 불확실하다.
- 다음에 확인해야 할 점
  - [explicit][높음] DimOS 재시작 후 browser hard refresh까지 한 상태에서 Zone A/B/C marker가 실제로 보이는지 확인해야 한다.
  - [explicit][높음] 현재 Zone A/B/C center가 simulation에서 reachable하고, inspection goal로 의미 있는 위치인지 확인해야 한다.
  - [inferred][중간] sensor event cooldown/deduplication이 같은 spreadsheet row를 반복 처리하지 않는지 runtime에서 확인해야 한다.
  - [inferred][중간] `inspect_zone` 실패 시 agent가 같은 mission을 반복 발화하거나 재실행하지 않는지 확인해야 한다.
- 충돌하는 요구사항
  - [explicit][높음] 사용자는 원래 “둥글게 돌면서 각 뷰 사진”을 원했지만, 실제 planner는 일부 viewpoint에서 `No path found`와 timeout을 냈다. 기능 완성도와 runtime 안정성이 충돌했다.
  - [explicit][높음] 사용자는 Spreadsheet를 사용하자고 했지만, 동시에 내부 이름에는 `sheet`를 쓰지 말라고 했다. 외부 임시 interface와 내부 장기 abstraction이 충돌했고, generic sensor naming으로 해소했다.
  - [inferred][중간] Zone marker는 costmap 기반 view 위에 그려져야 하지만, Zone 좌표가 costmap 밖에 있어도 보여야 한다. costmap 정확한 scale 유지와 operational landmark visibility가 충돌했고, bounds를 Zone까지 포함하는 transform으로 해소했다.

## 5. 최종적으로 복원한 현재 기준

- 현재 채택된 개발 방향
  - [explicit][높음] 외부 sensor feed를 polling하는 monitor가 rule/threshold 기반으로 high-level mission event를 만든다.
  - [explicit][높음] mission event는 agent message queue에 들어가고, agent는 `inspect_zone` skill을 호출한다.
  - [explicit][높음] Spreadsheet는 임시 input interface이고, 내부 module/데이터 모델은 generic sensor monitor/event로 유지한다.
  - [explicit][중간] Zone A/B/C는 reusable zone definition으로 관리하고, inspection skill과 command center marker가 같은 semantic source를 사용한다.
  - [inferred][중간] 현재 안정화 기준은 “event detection -> agent mission -> known zone inspection -> image output path 확인”의 end-to-end 경로를 먼저 신뢰 가능하게 만드는 것이다.
- 현재 우선순위
  - [explicit][높음] sensor event가 중복/과잉 없이 agent에게 전달되는 것.
  - [explicit][높음] `inspect_zone`이 실제 simulation 좌표계에서 도달 가능한 target을 사용하고 실패 시 명확한 message를 반환하는 것.
  - [explicit][높음] Zone A/B/C marker가 command center에 보여서 좌표와 navigation 문제를 사람이 디버깅할 수 있는 것.
  - [explicit][중간] 사진 저장 위치를 사용자가 직접 확인할 수 있게 skill output directory를 명확히 하는 것.
- 현재 비목표(non-goal)
  - [explicit][높음] MuJoCo 내부에 temperature/environment variable을 직접 주입하는 것은 현재 비목표다.
  - [explicit][높음] Spreadsheet 자체를 장기 internal abstraction으로 삼는 것은 비목표다.
  - [inferred][중간] sensor monitor가 low-level robot command를 직접 발행하는 것은 현재 설계 방향이 아니다.
  - [inferred][중간] agent가 매번 low-level move/rotate/capture step을 즉석 조합하게 하는 것도 현재 방향이 아니다.
  - [inferred][낮음] 모든 이동 중 camera frame을 개별 jpg로 저장하는 것은 명시된 목표가 아니다. 명시적 inspection capture와 spatial memory 저장은 구분된다.
